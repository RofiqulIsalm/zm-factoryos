# ZM FACTORYOS

## MASTER MD ACCOUNT + USER ACCOUNT MANAGEMENT & SECURITY SYSTEM

Add a secure and professional account architecture to the ZM FactoryOS application.

This requirement is CRITICAL.

The system must have one initial Master MD account that controls the creation and management of all other application users.

Do NOT create a system where every employee can independently register.

There must be NO public registration page.

Only authorized MD/Admin users can create employee accounts.

============================================================

1. MASTER MD ACCOUNT
   ============================================================

When the application is initially installed, create ONE Master MD account through a secure first-run setup or environment-based initialization.

The Master MD account represents:

Managing Director / MD

The Master MD account must have the highest level of application authority.

Example initial credentials for development only:

Username:
MD

Password:
A secure temporary password supplied during setup.

IMPORTANT:

Do NOT hardcode a real production password into source code.

Do NOT display the Master MD password publicly.

Do NOT expose it in the frontend.

For development, credentials may be configured through environment variables or a secure first-run setup.

Example:

INITIAL_MD_USERNAME
INITIAL_MD_PASSWORD

The application should require the MD to change the temporary password after first login.

============================================================
6. USERNAME RULES
=================

Usernames must be unique.

The database must enforce uniqueness.

Do not allow:

two users with the same username.

Username should be normalized where appropriate.

Example:

rahim
Rahim

should not accidentally create two accounts if the application
treats usernames case-insensitively.

============================================================
7. PASSWORD SECURITY
====================

Passwords must NEVER be stored as plain text.

Use:

Argon2

or

bcrypt

with appropriate security settings.

The database should store only password hashes.

Never return password hashes through API responses.

Never show password hashes in the frontend.

============================================================
8. PASSWORD CREATION
====================

When MD creates an employee account, MD may set a temporary password.

The system should support:

"Require password change on first login"

If enabled:

User logs in with temporary password.

System redirects to:

/change-password

The user must create a new password.

Then the account becomes normal.

============================================================
18. MASTER ACCOUNT RECOVERY
===========================

Do NOT create an unsafe "forgot password" mechanism.

If password recovery is implemented:

Use a secure reset-token system.

Reset tokens must:

* be random
* expire
* be single-use
* never be stored in plain form if practical

For production deployment, support secure email-based password reset
if email infrastructure is configured.

If email is not configured, provide a secure administrator recovery
procedure rather than exposing a secret reset URL publicly.

============================================================
19. SESSION SECURITY
====================

Use secure server-side authentication/session handling.

After login:

Create authenticated session.

Protect routes.

Examples:

/md
/md/users
/accounting
/billing
/reception

must require authentication.

If session expires:

Redirect to login.

Do not allow browser back navigation to expose sensitive data after
logout where practical.
